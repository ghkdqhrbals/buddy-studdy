# BuddyStudy PRD

## Purpose

BuddyStudy is a quiet AI tutor for people who use AI heavily but still want to keep their own knowledge sharp. The product asks short questions on a schedule, lets the user answer when convenient, grades the answer with OpenAI, and turns the accumulated record into topic-level learning statistics. Pro members can also hold a live two-way voice lesson with an AI tutor. Verified voice exchanges and ordinary questions are two types of the same learning record, visible in Records and their saved study tree, with the same publication and comment actions. The full session result remains private, and a private call recording requires explicit per-call consent.

## Product Principles

- Keep the app useful from the first screen, not as a marketing surface.
- Never steal the user's current answer draft when a new question arrives.
- Prefer compact, predictable controls over decorative UI.
- Treat statistics as the core feedback loop.
- Make backend sync understandable and recoverable.
- Keep settings simple enough to scan repeatedly.

## Supported Platforms

- iOS app built with SwiftUI `TabView`.
- macOS menu bar app built with SwiftUI `MenuBarExtra`, currently kept in the repository with public release paused.
- Shared model, storage, backend API, and notification services.

## Release Scope

- Current public release target: iPhone app through App Store Connect.
- The first Pro Voice Tutor release supports foreground sessions only. Moving the app to the background or locking the device ends the live lesson safely; background audio calling is not part of this release.
- macOS DMG/Sparkle release is on hold until the macOS sync/update experience is revisited.

## Core User Flows

### First Launch

1. On a fresh installation, the app enters Home immediately in the first supported iOS preferred language (`ko`, `en`, or `ja`) and falls back to English.
2. First launch starts with an empty study list. The first root study is created only after an explicit root-add action in My Studies, an authenticated external `create_root_study` request, or one semantically clear, current learner choice in Voice Tutor to begin a named topic as a new saved study. Voice creation does not require imperative grammar, literal create/save/root words, restatement, or a second confirmation; settings, device registration, a bare topic mention, ordinary interest, topic discovery, a recommendation request, a tutor suggestion, contextual agreement and lesson connection must never materialize a fallback study.
3. The user can change the app language later in Profile settings. An explicit saved choice is never overwritten by later device-language changes.

### Study

1. User receives or manually creates a study question through the backend.
2. User writes an answer draft that is preserved automatically.
3. User can reveal the hint on demand.
4. User submits for grading. The backend accepts and persists the answer
   immediately, changes the question lifecycle from `UNGRADED` to `GRADING`,
   appends the lifecycle transition to the durable question event history, then
   grades it asynchronously through the event outbox. The API also exposes
   the finer `gradingStatus` (`QUEUED`, analysis stages, `COMPLETED`, or
   `FAILED`), the active `correlationId`, and the latest event cursor without
   treating the editable draft as a submitted answer.
5. The app polls grading every three seconds by the persisted correlation ID
   returned with the accepted answer. Each request includes the last received
   event cursor, so intermediate durable stages are not skipped, and the
   completed AI decision is reconciled from the record API without replacing
   the user's draft. Polling belongs to the answer/detail screen that started
   it and stops immediately when that screen disappears, while an accepted
   submission request itself is allowed to finish persisting. Reopening the study
   room calls `GET /api/v1/studies/{studyId}` instead of loading the whole study
   tree. The response contains the pending question, including its persisted
   answer, grading request ID, and current grading status, plus the latest
   completed question. The app resumes polling for a pending submitted answer;
   when no pending question exists it keeps showing the latest completed
   question, user answer, and AI response.
6. Grading result, feedback, and explanation are stored in records.
7. Ungraded pending questions are capped at 3.
8. Home exposes separate All Studies, My Studies, and My Study Tree scopes. My Studies preserves the compact hierarchical topic outline, while My Study Tree renders the selected root as an interactive node graph whose orientation can be switched between vertical and horizontal.
9. A root study owns the question schedule, OpenAI model, and the single question flow. The backend owns the question prompt; iOS study creation and editing do not expose prompt overrides. Descendant nodes own only their topic, difficulty level, ordering, and question-rotation activation.
10. Adding a tree node opens GPT topic recommendations by default. The user can select one or more recommendations and add them together with one shared difficulty, or switch to manual topic entry. Duplicate normalized topic names are rejected across the user's studies.
11. Topic recommendations use a shared system catalog before generating new entries. The catalog manages up to five descendant levels and up to ten children per opened branch; missing children are generated once and become reusable suggestions. If the external suggestion provider is unavailable, the API still returns localized, parent-scoped fallback topics so child-topic creation is not blocked.
12. The user's study tree materializes selected catalog topics lazily so a five-level catalog never creates an exponential number of unused user nodes. New root and descendant nodes participate in question rotation by default.
12. Any number of tree nodes can participate in scheduled questions. The backend rotates through active nodes by least-recent selection, skips nodes already at their pending-question limit, and backs off only when every active node is blocked; an inactive node can still be opened for explicit manual question generation.
13. Generated questions are stored under the root study and retain the selected node's topic and difficulty. Level is communicated with restrained color instead of decorative icons.
14. Tree nodes are circular. The tree supports vertical/horizontal layout, pinch and button zoom, draggable saved positions, layout reset, and multi-select activation, pause, and deletion.
15. Root creation, descendant topic creation, and question generation are separate API/client methods. Creating a root or descendant never consumes monthly question allowance.
16. The Profile page shows a compact current-tier quota summary at the top, including remaining count, progress, and exact reset time. Selecting the summary opens Membership Management as a sheet. When the allowance is exhausted, question creation is blocked with a localized inline explanation.
17. Membership allowances are TIER1 30, TIER2 300, and TIER3 1,000 questions per monthly question window. TIER2 and TIER3 also include Pro Voice Tutor with a server-owned default allowance of 3,600 seconds (60 minutes) in a separate monthly voice window anchored to account creation; TIER1 has no Voice Tutor allowance. TIER2 and TIER3 each offer one monthly StoreKit subscription. The membership screen presents the current question and Voice Tutor allowances and both paid tiers as a compact single list with no billing-period selector, plus one primary subscribe/change action only when another tier is selected. Before purchase it clearly shows each tier name, monthly period, localized price, included monthly question and voice allowances, automatic-renewal disclosure, and direct Terms of Use and Privacy Policy links. The active plan and both quotas are read only from `GET /api/v1/billing/status` and `GET /api/v1/voice-tutor/status`; RevenueCat SDK state is limited to products, purchase, restore, and Customer Center. A paid purchase creates a `NORMAL/WAITING` invoice (`PREPARED`) before RevenueCat presents the purchase. iOS then sends RevenueCat's transaction identifier to the invoice confirmation API; server-side RevenueCat verification and the shared payment use case advance it through `VERIFIED` to `FULFILLED`. The same use case handles at-least-once RevenueCat webhooks, with event ID and transaction ID deduplication providing eventual consistency regardless of delivery order. Unpaid checkouts expire as `FAILED`; completed charges never regress because projection fails and never trigger an automatic refund. Refunds use separate linked `REFUND` invoices. Monthly question quota policy v5 keeps one `user_quota` current-state row and appends every mutation to `user_quota_history`; `quota_reservations` retains the exactly-once Saga identity and the period in which work was accepted. Voice Tutor time uses a separate server-authoritative seconds-based projection and reservation lifecycle. A verified effective-tier change preserves each domain's usage and reservations; question quota changes inside its existing fulfillment flow, while Voice Tutor reconciles its tier and base on the next status, history/detail, or session-start access. The managed one-minute rollover remains question-only, and Voice Tutor applies its natural monthly boundary lazily after reconciling an expired session. Every generated system question is reserved, committed, or released exactly once by Saga correlation ID, every voice session is reserved and settled exactly once by session identity, and effective tier reconciliation is idempotent. A partial billing application returns an explicit error while preserving verified payment evidence for retry; iOS must not convert this failure into an approval-pending message.
18. Root study rows omit level metadata. Level is presented only where it affects a specific tree topic.
19. A tree node with an unanswered question shows one red badge at its upper-right corner; the node action menu remains separate at the lower-right corner.
20. Study deletion is available only inside the study editor and executes immediately when the destructive row is tapped, without a second confirmation popover.
21. Manual question generation immediately shows an inline conversation-style loading message for the selected topic until the request completes.
22. When asynchronous question generation or localization exhausts its retry budget, the backend must publish a durable rollback event. Its consumer removes any unusable generated question, restores the coverage reservation and monthly question allowance exactly once, and only then exposes the failed process as terminal so the user can request another question for that topic.
23. Question, hint, grading feedback, and explanation content supports Markdown for emphasis, lists, and code while remaining backward-compatible with existing plain-text records.
24. The compact My Studies outline keeps the card, row geometry, and dividers fixed while newly selected branch contents settle in with a subtle direction-aware stagger; it does not blink or overlay old and new rows. Long-pressing every study card presents Edit, View Full Tree, and Delete actions; View Full Tree is not duplicated as an inline list row and remains available for childless roots so the user can enter the tree and add the first child topic. Roots without children omit only the empty child-topic section. After entering any study topic, the trailing toolbar keeps New Question and a separate More menu visible; More provides only Edit Study and View Full Tree for the containing root. Topic deletion remains inside the study editor.
25. Before the backend study hierarchy is available, My Studies shows an initial loading state. A failed hierarchy request shows a retryable error without exposing persisted descendant topics as independent root-study cards; an ordinary refresh keeps an already loaded hierarchy visible.

### Pro Voice Tutor

1. An authenticated member with an effective TIER2 or TIER3 entitlement can start a live, two-way voice call without selecting a topic first. The tutor's first utterance is a direct topic-discovery question in the accepted session language, without a greeting or self-introduction; it then finds the learner's saved topic and follows its actual child branches conversationally. An empty saved-study list does not block connecting and never creates a fallback study. TIER1 receives a localized Pro-upgrade explanation and no realtime credential or stream allocation.
2. The first release is foreground-only. iOS requests microphone permission immediately before the first lesson, uses the BuddyStudy voice-session API while the lesson screen is active, and ends the session when the app backgrounds, the device locks, the account changes, or the screen is dismissed. Audio background mode and unattended continuation are out of scope.
3. `GET /api/v1/voice-tutor/status` is the client authority for availability, remaining seconds, reset time, the operator-configured per-session ceiling, and optional-recording availability. `POST /api/v1/voice-tutor/sessions` derives and atomically reserves the next-session maximum as no more than the smaller of the remaining monthly allowance and that ceiling. New iOS clients POST an audio-only SDP offer to `/api/v1/voice-tutor/sessions/{id}/webrtc`, carry microphone/model media directly over the resulting OpenAI WebRTC peer connection, and use the authenticated `/control` WebSocket with `buddystudy.voice.control.v2` for server-owned turn control and lifecycle. Both requests require `X-Voice-Turn-Protocol: local-vad-v1`; an older client is rejected before creating or claiming a provider call. `/stream` with `buddystudy.voice.v1` remains the bounded PCM fallback.
4. Voice allowance is counted in integer seconds. The server-owned plan default is 3,600 seconds per monthly window for both TIER2 and TIER3 and zero for TIER1. Operators can change each tier's `monthlyVoiceSecondsLimit` without an app release and can set a nullable per-user monthly override without resetting that user's period or counters. The exact administrative override value `31,536,000` seconds is presented by the app as effectively unlimited rather than as rounded minutes; it does not remove the per-call provider ceiling. `VOICE_TUTOR_MAX_SESSION_SECONDS` independently changes the operational cap for one call, defaults to 3,600 seconds, and is hard-clamped to the provider's 60-minute Realtime session limit. The default 60 monthly minutes may be used in one call or split across shorter calls. Apart from the effectively-unlimited convention, the app displays rounded minutes but never calculates entitlement or authoritative usage locally.
5. The server timestamps the accepted session, owns the WebRTC call and authenticated sideband lifecycle, reserves capacity transactionally, and settles server-observed rounded-up connected time exactly once. The reservation freezes whether that session will exhaust its finite monthly allowance at its hard end, so a normal per-call/provider deadline is never misreported as monthly exhaustion. The legacy PCM fallback additionally meters accepted decoded PCM and charges the greater value. It releases unused reservation after normal end or failure and expires abandoned sessions. Concurrent starts cannot reserve the same remaining seconds twice, and client-provided duration never determines charged usage.
6. Voice Tutor is independent from question creation and answer grading. Starting, ending, summarizing, or syncing a voice lesson consumes no question quota, creates no pending question, and never reads, submits, clears, replaces, or otherwise mutates the active answer draft or its record-ID-keyed persistence.
7. Ending a session explicitly through `POST /api/v1/voice-tutor/sessions/{id}/end`, or implicitly through a terminal stream close, always settles the call but produces a private Tutor Learning Result only after the server has authorized one substantive question for a confirmed saved focus, semantically verified the exact completed tutor-audio item as that one question, and durably linked the learner's exact complete answer to it. If no such actual question-and-answer exchange exists, the backend must not invoke the summary model, regardless of transcript length or whether setup actions succeeded. A long answer may span multiple persisted parts, but the parts qualify only as one ordered, duplicate-free, same-revision set with no intervening tutor turn; the result model and canonical projector must accept all of that set or none of it. Topic discovery, root/topic creation, settings changes, focus selection, consent and other setup-only dialogue never qualify as learning: they skip the summary model, complete with an empty technical result so clients stop polling, and create neither a canonical nor public record. Eligible sessions expose only the source-backed question, complete learner answer, and any exact validated final feedback to the bounded summary request; their validated node-linked exchanges become canonical `VOICE_TUTOR` records alongside `QUESTION` records, not a second collection of posts. Full transcripts, session/turn identities and recordings remain owner-only. Spoken assessments do not enter ordinary generated-question or topic-growth calculations without an explicit assessment policy.
8. Realtime microphone/model frames are never written to MySQL, application logs, analytics, Sentry, MCP, or backups. Optional recording is a separate default-off capability: only a session created with explicit `voice-recording-v1` consent may mix the learner and tutor tracks locally into one AAC/M4A file and upload it directly to private S3. The backend validates signed content type, exact length, and SHA-256 before making it available; the owner receives only short-lived playback URLs, may delete it immediately, and the default configurable retention is 30 days from the server-recorded call end. Reissuing the same pending upload grant cannot extend that absolute deadline, and playback grants fail closed at the boundary. Account withdrawal first commits an independent permanent recording-prefix cleanup tombstone, attempts private-object deletion, continues relational cleanup even if S3 is unavailable, retries deletion minutely through the signed-URL expiry safety deadline and daily forever afterward, and requires bucket lifecycle expiry as a storage-level backstop. Bounded transcript turns and the derived result may still be stored for private lesson history, while voice endpoint bodies, SDP, control frames, transcript text, summaries, object keys, presigned URLs, and provider credentials stay excluded from API/external-provider logs, analytics, and Sentry attachments.
9. The MCP server exposes authenticated, owner-scoped, read-only `list_voice_tutor_sessions`, `get_voice_tutor_session`, and `get_voice_tutor_quota` tools plus the `buddystudy://voice-tutor/sessions/recent` and `buddystudy://voice-tutor/quota` resources. MCP may return ordinary owner-scoped recording metadata through session detail, but never an audio object, object key, upload grant, or presigned playback URL; it never starts, streams, reconnects, ends, extends, records, downloads, or deletes a voice session.
10. Microphone denial, an interrupted audio route, network loss, quota exhaustion, and provider failure all produce explicit recoverable or terminal states. When the reserved session reaches actual monthly exhaustion during a live WebRTC call, the server closes learner input, asks the tutor to speak one short localized exhaustion notice, and identifies that exact response on the sanitized control stream. Settlement and transport teardown wait for that marked provider response to complete, its output audio buffer to stop, and the client to acknowledge that the same response's local playout has drained. When monthly exhaustion and the provider's 3,600-second hard limit are the same boundary, the server may pre-arm the notice up to eight seconds before hard end; that notice consumes the final reserved service seconds, the client keeps showing their countdown, and settlement occurs at the exact hard boundary. A notice generation that produces no audible evidence within three seconds is cancelled and retried exactly once, while a notice that has started speaking is allowed to finish without regeneration. An ordinary 60-minute per-call/provider `TIME_LIMIT` remains distinct, must not claim the monthly allowance is exhausted, and follows its own terminal path. A reserved session has one relay claim: a disconnect is finalized and a retry creates a new session from the remaining monthly allowance, rather than opening a second provider socket against the old reservation. A final result and quota settlement remain idempotent when end requests race or repeat.
11. A learner who starts speaking over the tutor does not stop or truncate the tutor's current audio. Every ordinary tutor response is one short, complete sentence; the app plays that sentence through while continuing to capture the learner, and the backend answers the coalesced committed learner turn only after the same response has reached provider completion, its OpenAI output buffer has stopped, and the learner has stopped. WebRTC provider turn detection is explicitly disabled and confirmed before ready because provider VAD can clear output despite disabled response interruption. The app automatically detects speech boundaries from its existing processed microphone path, independently of recording consent, and sends only numbered start/stop signals; no push-to-talk action is required and tutor speech never mutes the microphone. The backend owns input commits and waits for their provider acknowledgement. Client-originated input commits/clearing, response cancellation, audio truncation, session updates, and response creation are rejected on `/control`; the direct WebRTC offer is audio-only, so provider control remains on the backend sideband. Long learner speech is split into bounded internal transcription checkpoints without stopping capture; elapsed time, a meaningful checkpoint or an important misconception never permits the tutor to speak over an ongoing utterance. Only the final stopped, acknowledged, assessed and persisted turn can open the normal reply gate.
12. Once media and control are ready, the tutor speaks first with only a short, direct topic-discovery question such as “어떤 주제로 이야기해 볼까요?” It does not greet, introduce/name itself, describe itself as an AI/tutor/teacher, use a lead-in, choose a predetermined topic, or require a readiness check. Only when the learner directly asks about its identity may it answer that identity question. An ordinary first topic-bearing learner utterance authorizes discovery only, even when it names a precise saved descendant or asks to begin it. The explicit exception is a semantically attested direct request in that same persisted turn to create one new root and start learning it immediately; that compound request follows the server-owned create/readback/focus pipeline in requirement 15. For ordinary saved-tree discovery, the tutor uses small owner-scoped search pages and exact parent/child relationships, follows a complete single-child chain without making the learner repeatedly choose, and at the first real branch speaks at most three actual returned children. It must then speak the exact verified endpoint or branch candidates and wait for one new final meaningful learner reply before selecting an exact target or teaching it. A contextual yes after that spoken proposal is sufficient and is not followed by another readiness check. A greeting such as “안녕”, a microphone check, the original broad request, tool arguments and ordinary tool-result text are neither target confirmation nor a lesson-ending command. Connection failure is never presented as successful lesson completion; cleanup preserves a retryable failure state, clears the live countdown, and refreshes the server-owned quota. Reserved time is distinguished from used time and released capacity is reflected after settlement.
13. The speaking indicator reflects locally rendered tutor audio, not just server-side generation. Continuous digital-silence buffers must not keep a completed sentence waiting indefinitely, while late or quiet real audio still postpones the next turn until it clears the device output latency. Diagnostics distinguish connection success, media rendering, and device playout without logging speech or credentials.
14. The live surface is a compact call, not a dashboard. Its ordinary mode centers one stateful tutor orb with small topic, state, remaining-time, conversation and end-call affordances around it; there is no user-facing mute control. Tapping the central orb is the primary `pause-v1` action: the UI remains in its pending state until the server ACK establishes pause, then shows a smaller static paused orb; tapping it again requests resume and restores live listening only after the matching server ACK and input-buffer fence. Conversation content is not a popup, drawer or sheet. Its action switches the same call destination into an in-call full-screen transcript mode with conventional learner-right and tutor-left dialogue, a direct return to the orb, stable remaining time and end-call access; scrolling dialogue cannot accidentally pause, resume or dismiss the call. The app tab bar is hidden while this destination is open. Learning-result details expand in place, without navigating away from or stopping the call. Connection/summary failures, recording and pause remain compact, explicit when actionable and available to VoiceOver. After settlement the time label clearly switches to the monthly allowance; an empty or still-reserved snapshot is never substituted for the live countdown. Call navigation is independent of whether reserving time removes the entry button.

15. The voice LLM is explicitly given the existing, authenticated BuddyStudy MCP study/record/statistics tools; opening the HTTP MCP server alone is not a model integration. It reads saved child topics with a parent-scoped, paginated `list_studies` call. A semantically clear current first-person choice to add one exact child under an unambiguous selected parent calls `create_study_topic` once in that turn without requiring imperative grammar, restatement or duplicate confirmation. The same rule applies to an unambiguous learner-chosen name or level change through `update_study`: natural language is sufficient and the exact choice executes without a second “확실한가요?” or contextual-yes round. Mere mentions, examples, recommendations, quotations, third-party wishes and ambiguous targets or outcomes are not write permission. When the tutor has just spoken exactly one server-read candidate, its exact target evidence remains available across consecutive persisted learner utterances until the next tutor response begins, so a learner may naturally complete the name/level/action over more than one turn or refer to “그 이름/이 주제” without repeating the old title. Each assessment sees only the bounded, ordered, learner-owned continuation available at its boundary; ambiguity, a different target, a new tutor response, failed persistence or a spent authorization clears it. Retained reference evidence is never itself write permission: both semantic decisions must attest the completed operation, after which the server mints one owner-, call-, revision- and exact-target-bound lease and consumes it once; the write still re-reads the owned node and applies its parent/title/level optimistic CAS. A direct choice to begin one named topic as a new saved root—including natural wording such as wanting to study it as something new—uses the owner-scoped, create-only `create_root_study` flow immediately: the learner's final persisted statement is the creation approval, so the tutor must not ask “만들까요?”, demand magic create/save/root words, or require a later contextual yes. The server's structured semantic input assessment, followed by an independent semantic attestation, extracts the exact topic directly present in that learner speech and the requested 1–10 level, applying default 5 only when omitted; neither decision is a regex, keyword-list, utterance-length or punctuation classifier. Each assessment also independently decides whether that same current turn unambiguously asks to start the newly created lesson now; both must agree before immediate start is authorized. The server binds those fields and that compound intent to one-shot leases, rejects mismatched tool arguments, and atomically consumes each lease immediately before its operation. Generic agreement, a tutor proposal, ordinary interest, topic discovery, recommendation requests, checkpoints and a newer tutor-response boundary cannot mint or reuse that authority. An exact normalized root duplicate is returned unchanged rather than updated; a matching child conflicts. Root creation consumes no question quota and does not by itself establish lesson focus. After the create result, the server bridge schedules an exact `get_study` read for the returned ID and withholds the tutor's spoken acknowledgment until both function outputs have been acknowledged and that readback proves the saved root. A missing or mismatched readback is reported only as an unverified outcome and never authorizes an automatic create retry. A create-only request then follows the ordinary path: the tutor speaks that exact saved root as a separate start offer, obtains a new agreement, and succeeds with `select_voice_study` before teaching it. When the same persisted turn was independently approved for both creation and immediate learning, `create_root_study` instead reports `AUTO_FOCUS_PENDING`; after the exact readback, the server—not the model—performs the bound `select_voice_study`. Only a successful `CREATED_ROOT_IMMEDIATE_START` focus result permits the first substantive question, with no repeated confirmation or readiness prompt. `update_study` patches only the chosen name and/or 1–10 level of an exact owned node in the verified call tree, preserving its identity, parent and other settings. When that same current persisted turn is independently approved for both the exact update and immediate learning, the prepared update reports `AUTO_FOCUS_PENDING` and the server—not the model—performs one bound selection against the exact post-update revision. Only `UPDATED_STUDY_IMMEDIATE_START` permits the first substantive question at the revised frozen name and level without another confirmation or readiness prompt. An update-only turn keeps the normal flow: a prepared current focus applies to the next new question, while an updated offered candidate still needs a fresh exact selection. A failed or mismatched post-update focus never replays the write, reuses the old start permission, or teaches from stale metadata; newer meaningful learner speech fences that pending permission, while noise or non-communicative audio cannot create it. `delete_study` remains the destructive exception: it first previews the named subtree and descendant count, asks for confirmation, and requires a new affirmative spoken reply after that question. Short-lived, single-use call-bound tokens prevent skipped deletion confirmation or replay; deletion also atomically compares the exact subtree so it cannot silently expand. Voice deletion is limited to 128 nodes; larger or unresolved trees use the tree screen. Changes are acknowledged only after a successful result. These requests never consume question quota, replace answer drafts, or start/end a call. While the call remains live, a verified new root is eligible for the existing sanitized `buddystudy.voice.study.changed` hint; its wire payload contains the event type, positive study ID, server-owned change kind and a bounded deleted-ID list, never tool output or study settings. iOS uses that hint to fetch the exact node through the normal study store. Existing normalized duplicates emit no false creation hint, and ordinary study sync remains authoritative if the live hint cannot be delivered. Prior answers, voice transcripts and results are retained.
   In requirement 15, failed persistence clears any mutation authority from that learner item, but it does not spend or erase the preceding unspent spoken-target evidence. That referent remains bounded by the same tutor-response boundary so a safely retried persisted continuation can still resolve it; it cannot authorize a write by itself.
16. A tool-only response is silent work, not tutor speech or a completed lesson. Its result must return to the LLM and be acknowledged before the next spoken reply; responses that contain audio still finish through the unchanged audio-buffer boundary. Call outcome and summary outcome are separate: a transport-failed session remains eligible only when it already contains a durable server-authorized study question and its exact complete learner answer, while setup-only dialogue completes without calling the summary model or creating a canonical/public record. A late socket-close error cannot overwrite an already accepted user end. The app follows explicit result status, not the existence of a placeholder, performs bounded rechecks, and refreshes cached history on re-entry; delayed/unavailable reads are not mislabeled as failed generation.
17. After the learner agrees to start, the tutor follows the learner's actual saved study tree and each node's configured 1–10 level. “Deeper” means exploring that tree's saved topics, not inventing advanced branches or automatically raising difficulty. A successful focus selection or explicit continue decision grants one server-owned question purpose; only a clean completed tutor-audio item independently verified as exactly one substantive question in that focus/revision is marked as the pending study question. The tutor waits for a semantic answer to that exact item. Answer-bearing checkpoints from one continuous utterance may be promoted only when its final event supplies the complete ordered set; a filler-only tail is not treated as another answer part, and a subset, duplicate, reordered part, revision mismatch or intervening tutor turn invalidates the claimed exchange. The tutor then gives a brief 0–100 spoken assessment with supported strengths, gaps or improvements and leaves space until it has actually finished playing. Feedback is source evidence only when one clean completed tutor item is independently verified against the exact question and full answer, persists against the final linked answer part in the same lesson revision, and has neither a later linked answer nor an intervening tutor turn. Only after the server verifies these identities may it inspect the persisted current node's real direct children, speak one actual child or a brief real branch choice, and use the learner's next final meaningful agreement to move exactly one verified edge without asking for an internal selection command. Silence, greetings, unrelated tutor rows, filler, readiness replies, hint requests, learner follow-up questions and an unanswered or unauthorized tutor question do not authorize progression, assessment, summary creation or topic creation. Siblings, ancestors, skipped descendants and other roots require a separately server-read, actually spoken and freshly confirmed exact target.
18. Each new learning result groups actual question/complete-answer/exact-feedback exchanges and learner-led follow-ups by explored topic, with a concrete account of what was examined. Saved topic identities, names, parent links and levels are immutable versioned context. An explicit in-call name/level change applies to the next new question; pending and completed questions retain their original level even when an answer or transcript arrives later. At most 32 combined focus/metadata revisions can be added in one call; unprepared metadata cannot authorize a new question. Read-only topic browsing never consumes the separate 64-node lesson snapshot limit. A server-owned revision is fixed at response/input creation, never inferred from transcript arrival time or supplied by the model. Summary character limits are applied only between complete verified exchange groups, never through the middle of a multipart answer or its exact feedback. The source-backed exchanges are also attached to their actual owned study-tree nodes, so My Studies and My Study Tree show ordinary and voice learning records together. Questions, learner answers and spoken feedback retain their original transcript text and source IDs; scores copy explicit assessments supported by the exact feedback, not a second grading pass. Unknown/deleted/ambiguous topics stay in private session history rather than being filed by matching text or creating nodes. Deleting the selected node does not terminate the call: new questions on deleted nodes stop until the learner chooses a verified surviving focus. Voice exchanges use the common record/publication contract below while remaining outside ordinary-question statistics, quota and drafts.
19. Node learning history is a bounded cursor page (30 entries in iOS), with an explicit option to include saved descendants. Read-only detail shows the question, answer, spoken score if supported, strengths, improvements and explored content. The existing content-translation stream builds language-specific text projections without overwriting the original or translating node identity, level or score. Original content stays readable while translation is pending or failed. Existing structured completed voice results can acquire these node records without regenerating or regrading their summaries.
20. The central tutor orb is the compact “Take a break”/continue control whenever the WebRTC server acknowledges `pause-v1`; no separate user-facing mute state competes with it. A tap closes microphone capture immediately, lets the current tutor response and pending input finish safely, and displays a stable paused state only after the matching server ACK. A second tap resumes capture only after a fresh input-buffer clear and matching ACK; it never replays paused silence or cancels/truncates tutor output. Each offered candidate carries server-private evidence of the exact single-child edges followed and, when applicable, the exact leaf read. ## Non-Goals

- Guaranteeing real-time push delivery independent of APNs behavior.
- Storing OpenAI billing balance locally as an authoritative source.
