# BuddyStudy PRD

## Purpose

BuddyStudy is a quiet AI tutor for people who use AI heavily but still want to keep their own knowledge sharp. The product asks short questions on a schedule, lets the user answer when convenient, grades the answer with OpenAI, and turns the accumulated record into topic-level learning statistics. Pro members can also hold a live two-way voice lesson with an AI tutor. Verified voice exchanges and ordinary questions are two types of the same learning record, visible in Records and their saved study tree, with the same publication and comment actions. The full session result remains private, and a private call recording requires explicit per-call consent.

## Product Principles

- Keep the app useful from the first screen, not as a marketing surface.
- Never steal the user's current answer draft when a new question arrives.
- Prefer compact, predictable controls over decorative UI.
- Treat statistics as the core feedback loop.
- Make backend sync understandable and recoverable.
- Keep settings simple enough to scan repeatedly.

## Supported Platforms

- iOS app built with SwiftUI `TabView`.
- macOS menu bar app built with SwiftUI `MenuBarExtra`, currently kept in the repository with public release paused.
- Shared model, storage, backend API, and notification services.

## Release Scope

- Current public release target: iPhone app through App Store Connect.
- The first Pro Voice Tutor release supports foreground sessions only. Moving the app to the background or locking the device ends the live lesson safely; background audio calling is not part of this release.
- macOS DMG/Sparkle release is on hold until the macOS sync/update experience is revisited.

## Core User Flows

### First Launch

1. On a fresh installation, the app enters Home immediately in the first supported iOS preferred language (`ko`, `en`, or `ja`) and falls back to English.
2. First launch starts with an empty study list. The first root study is created only after an explicit root-add action in My Studies, an authenticated external `create_root_study` request, or a semantically clear Voice Tutor new-study request followed by one exact spoken confirmation question and fresh natural agreement. Voice intent needs no imperative grammar, literal create/save/root words or repeated command; a natural “응/네/그렇게 해” may confirm the unchanged pending proposal. Settings, device registration, a bare topic mention, ordinary interest, topic discovery, a recommendation request, an unrelated acknowledgement and lesson connection must never materialize a fallback study.
3. The user can change the app language later in Profile settings. An explicit saved choice is never overwritten by later device-language changes.

### Study

1. User receives or manually creates a study question through the backend.
2. User writes an answer draft that is preserved automatically.
3. User can reveal the hint on demand.
4. User submits for grading. The backend accepts and persists the answer
   immediately, changes the question lifecycle from `UNGRADED` to `GRADING`,
   appends the lifecycle transition to the durable question event history, then
   grades it asynchronously through the event outbox. The API also exposes
   the finer `gradingStatus` (`QUEUED`, analysis stages, `COMPLETED`, or
   `FAILED`), the active `correlationId`, and the latest event cursor without
   treating the editable draft as a submitted answer.
5. The app polls grading every three seconds by the persisted correlation ID
   returned with the accepted answer. Each request includes the last received
   event cursor, so intermediate durable stages are not skipped, and the
   completed AI decision is reconciled from the record API without replacing
   the user's draft. Polling belongs to the answer/detail screen that started
   it and stops immediately when that screen disappears, while an accepted
   submission request itself is allowed to finish persisting. Reopening the study
   room calls `GET /api/v1/studies/{studyId}` instead of loading the whole study
   tree. The response contains the pending question, including its persisted
   answer, grading request ID, and current grading status, plus the latest
   completed question. The app resumes polling for a pending submitted answer;
   when no pending question exists it keeps showing the latest completed
   question, user answer, and AI response.
6. Grading result, feedback, and explanation are stored in records.
7. Ungraded pending questions are capped at 3.
8. Home exposes separate All Studies, My Studies, and My Study Tree scopes. My Studies preserves the compact hierarchical topic outline, while My Study Tree renders the selected root as an interactive node graph whose orientation can be switched between vertical and horizontal.
9. A root study owns the question schedule, OpenAI model, and the single question flow. The backend owns the question prompt; iOS study creation and editing do not expose prompt overrides. Descendant nodes own only their topic, difficulty level, ordering, and question-rotation activation.
10. Adding a tree node opens GPT topic recommendations by default. The user can select one or more recommendations and add them together with one shared difficulty, or switch to manual topic entry. Duplicate normalized topic names are rejected across the user's studies.
11. Topic recommendations use a shared system catalog before generating new entries. The catalog manages up to five descendant levels and up to ten children per opened branch; missing children are generated once and become reusable suggestions. If the external suggestion provider is unavailable, the API still returns localized, parent-scoped fallback topics so child-topic creation is not blocked.
12. The user's study tree materializes selected catalog topics lazily so a five-level catalog never creates an exponential number of unused user nodes. New root and descendant nodes participate in question rotation by default.
12. Any number of tree nodes can participate in scheduled questions. The backend rotates through active nodes by least-recent selection, skips nodes already at their pending-question limit, and backs off only when every active node is blocked; an inactive node can still be opened for explicit manual question generation.
13. Generated questions are stored under the root study and retain the selected node's topic and difficulty. Level is communicated with restrained color instead of decorative icons.
14. Tree nodes are circular. The tree supports vertical/horizontal layout, pinch and button zoom, draggable saved positions, layout reset, and multi-select activation, pause, and deletion.
15. Root creation, descendant topic creation, and question generation are separate API/client methods. Creating a root or descendant never consumes monthly question allowance.
16. The Profile page shows a compact current-tier quota summary at the top, including remaining count, progress, and exact reset time. Selecting the summary opens Membership Management as a sheet. When the allowance is exhausted, question creation is blocked with a localized inline explanation.
17. Membership allowances are TIER1 30, TIER2 300, and TIER3 1,000 questions per monthly question window. TIER2 and TIER3 also include Pro Voice Tutor with a server-owned default allowance of 3,600 seconds (60 minutes) in a separate monthly voice window anchored to account creation; TIER1 has no Voice Tutor allowance. TIER2 and TIER3 each offer one monthly StoreKit subscription. The membership screen presents the current question and Voice Tutor allowances and both paid tiers as a compact single list with no billing-period selector, plus one primary subscribe/change action only when another tier is selected. Before purchase it clearly shows each tier name, monthly period, localized price, included monthly question and voice allowances, automatic-renewal disclosure, and direct Terms of Use and Privacy Policy links. The active plan and both quotas are read only from `GET /api/v1/billing/status` and `GET /api/v1/voice-tutor/status`; RevenueCat SDK state is limited to products, purchase, restore, and Customer Center. A paid purchase creates a `NORMAL/WAITING` invoice (`PREPARED`) before RevenueCat presents the purchase. iOS then sends RevenueCat's transaction identifier to the invoice confirmation API; server-side RevenueCat verification and the shared payment use case advance it through `VERIFIED` to `FULFILLED`. The same use case handles at-least-once RevenueCat webhooks, with event ID and transaction ID deduplication providing eventual consistency regardless of delivery order. Unpaid checkouts expire as `FAILED`; completed charges never regress because projection fails and never trigger an automatic refund. Refunds use separate linked `REFUND` invoices. Monthly question quota policy v5 keeps one `user_quota` current-state row and appends every mutation to `user_quota_history`; `quota_reservations` retains the exactly-once Saga identity and the period in which work was accepted. Voice Tutor time uses a separate server-authoritative seconds-based projection and reservation lifecycle. A verified effective-tier change preserves each domain's usage and reservations; question quota changes inside its existing fulfillment flow, while Voice Tutor reconciles its tier and base on the next status, history/detail, or session-start access. The managed one-minute rollover remains question-only, and Voice Tutor applies its natural monthly boundary lazily after reconciling an expired session. Every generated system question is reserved, committed, or released exactly once by Saga correlation ID, every voice session is reserved and settled exactly once by session identity, and effective tier reconciliation is idempotent. A partial billing application returns an explicit error while preserving verified payment evidence for retry; iOS must not convert this failure into an approval-pending message.
18. Root study rows omit level metadata. Level is presented only where it affects a specific tree topic.
19. A tree node with an unanswered question shows one red badge at its upper-right corner; the node action menu remains separate at the lower-right corner.
20. Study deletion is available only inside the study editor and executes immediately when the destructive row is tapped, without a second confirmation popover.
21. Manual question generation immediately shows an inline conversation-style loading message for the selected topic until the request completes.
22. When asynchronous question generation or localization exhausts its retry budget, the backend must publish a durable rollback event. Its consumer removes any unusable generated question, restores the coverage reservation and monthly question allowance exactly once, and only then exposes the failed process as terminal so the user can request another question for that topic.
23. Question, hint, grading feedback, and explanation content supports Markdown for emphasis, lists, and code while remaining backward-compatible with existing plain-text records.
24. The compact My Studies outline keeps the card, row geometry, and dividers fixed while newly selected branch contents settle in with a subtle direction-aware stagger; it does not blink or overlay old and new rows. Long-pressing every study card presents Edit, View Full Tree, and Delete actions; View Full Tree is not duplicated as an inline list row and remains available for childless roots so the user can enter the tree and add the first child topic. Roots without children omit only the empty child-topic section. After entering any study topic, the trailing toolbar keeps New Question and a separate More menu visible; More provides only Edit Study and View Full Tree for the containing root. Topic deletion remains inside the study editor.
25. Before the backend study hierarchy is available, My Studies shows an initial loading state. A failed hierarchy request shows a retryable error without exposing persisted descendant topics as independent root-study cards; an ordinary refresh keeps an already loaded hierarchy visible.
26. Opening a topic from My Studies or My Study Tree prepares its question, answer state, saved draft, quota and first available learning-record page before pushing the detail screen. The selected tree node shows a compact loading indicator while the tree and its back navigation remain in place. A failed load keeps the current screen available for retry; leaving or selecting another node cancels the previous opening. The answer input and saved draft are present in the destination's first layout, and prepared detail/history are not immediately fetched again.

### Pro Voice Tutor

#### Current conversation contract — `realtime-native-v1`

This is the active iOS voice contract. The realtime model hears the full conversation and decides meaning, turn intent, topic choice and tool use itself. No separate live GPT intent, filler, consent, question or feedback classifier gates a normal response. The detailed independently attested offer/lease and approved-input rules retained below describe only the legacy `local-vad-v1`/PCM implementations; they do not apply to this native conversation path. Entitlement, quota, foreground lifecycle, recording privacy, drafts and common learning-record ownership remain shared requirements.

- iOS negotiates `X-Voice-Turn-Protocol: realtime-native-v1` on both SDP and control. Local Silero speech detection and backend-owned manual commits remain in place to avoid the provider-VAD audio cut-off. Preserve the learner's turn through 1.28 seconds of acoustic quiet, then require a further 400 ms of server-observed quiet before starting a normal response. Returning speech restarts that wait; commit acknowledgement alone never authorizes a reply. This automatic turn policy applies outside an active saved-question answer; manual answer capture below overrides it. Opening, tool continuations and provider retries share this gate. Responses use the realtime conversation without waiting for final ASR, SQL persistence or a second model call. The same realtime model treats a mid-thought pause as a reason to stay silent, while accepting clearly complete short answers. Transcripts are saved asynchronously as original evidence, without regex-based meaning filters or rewriting.
- A learner can interrupt an ordinary tutor response by speaking naturally. Local speech onset silences the current tutor output immediately while microphone capture and the WebRTC connection stay active. The backend cancels that response and clears its queued provider audio; the interrupted response must not resume, retry, execute pending tools or become a completed tutor transcript. The latest committed learner turn may receive a fresh reply after the learner stops and cancellation/clear acknowledgements arrive, without waiting for the old spoken answer to finish. The existing numbered speech protocol remains unchanged; `buddystudy.voice.response.interrupted` with `responseId` synchronizes the interrupted response on the control stream. Explicit pause and terminal quota/end-call audio keep their existing lifecycle.
- The realtime model distinguishes contextual short acknowledgements, names, numbers and questions from ambient noise or noncommunicative hesitation. Noise/filler-only input can produce an empty silent response and no tool call; it never approves a proposal, starts learning or ends a call. This is conversational model judgment, not a regex, blacklist or minimum sentence-length rule.
- Begin with “어떤 주제로 이야기해 볼까요?” in Korean, or its session-language equivalent, without self-introduction. Read actual saved topics when asked, follow their saved parent-child tree naturally and select the learner's chosen exact node with `select_voice_study`; no special selection sentence or extra readiness confirmation is required. A lookup alone is not a request to quiz, and creation alone does not select a lesson.
- Profile settings expose one compact **Default call language** choice: follow app language, Korean, English or Japanese. Save/Cancel applies normally; the saved choice governs the next call and voice previews independently of the app's interface language. Resolve and freeze it before call setup can suspend, preserving it across authentication recovery. Keep spoken explanations, confirmations and error notices in the selected language, including special question-readback responses; short foreign words, uncertain audio and tool output must not silently change it. Foreign quotations and technical terms can retain their original language. The setting controls both input-transcription configuration and spoken-output instructions; it does not guarantee perfect recognition or model language adherence.
- The realtime model can prepare root/child creation, topic rename, level change and subtree deletion using `prepare_voice_study_mutation`. Understand ordinary references and natural new-study wishes; ask only for genuinely missing or ambiguous business details, not a repeated command. The server resolves ownership and freezes the exact action, node/parent and fields, then returns a short confirmation question. Preparation changes nothing.
- Ask that question once, wait for its audio to finish and accept natural agreement such as “응”, “네” or “그렇게 해”. The same realtime model interprets the reply and calls `confirm_voice_study_mutation` with the unchanged proposal ID and a boolean decision. A refusal cancels; silence, filler, unrelated speech and quotes are not agreement. Changed details require a new proposal. Actual execution retains immutable fields, a session/device/authentication boundary, expiration, at-most-once consumption and saved-data revision checks. Report the verified result briefly, without server/permission explanations or repeated confirmation.
- For “create/change this and start studying”, include starting in the one confirmation question, then select the exact returned saved node after the confirmed write and start without another readiness exchange. Editing an unrelated topic leaves the current lesson intact; editing the selected topic changes only subsequent questions' frozen level. Deletion preserves earlier learning records and does not end the call.
- After selecting an exact saved topic, check its canonical pending questions first. Read the saved question faithfully, without its hint or an improvised replacement. A question that arrived earlier keeps its original topic and level even if the topic's current level has changed. A fresh learner request to skip uses `skip_question` for that exact unanswered question; skipping alone neither generates a replacement nor spends question allowance.
- If no ready unanswered question remains and the learner wants a new one, use the ordinary `request_question` flow and wait for its exact generation correlation ID to yield a saved question. This consumes the normal question allowance and uses a server-derived idempotency key for the learner request. After the saved question finishes playing, keep listening until the learner taps **Finish answer** on the orb. Silence and long-answer transcription checkpoints must never trigger a tutor reply, submit an answer, or switch questions. Show one editable answer draft during capture and review; learners can correct earlier text without late ASR replacing their edits. Capture must be visually distinct from ordinary conversation even before the first word: a warm amber orb, persistent microphone/ring cue and a short explanation that pauses do not finish the answer. The cue follows the trusted answer-capture state, remains visible during thinking pauses and disappears during microphone pause or review; color alone must not carry this meaning. Finish stops microphone capture and waits for final recognition before review. Only the learner's explicit **Submit** sends that reviewed text through canonical answer submission; the realtime model cannot call `submit_answer` to submit on their behalf. Empty drafts cannot submit, and answers over 8,000 UTF-16 code units remain editable so the learner can shorten them. An explicit skip control skips the current question without requiring a spoken answer, replacement generation, or question quota. Poll its canonical grading correlation and read the saved score and feedback instead of making up a spoken assessment. Leave space afterward and explain follow-ups without treating them as new submitted answers. Greater depth follows actual saved children through one-edge `advance_voice_study`.
- The backend publishes one ordered call/lesson display snapshot: ordinary conversation; pending-question lookup, generation, saved-ready and readback; answer capture, final recognition, editable review and explicit submission; canonical grading and saved completion; operation failure and call termination. Pause preserves the underlying lesson stage. iOS shows a restrained orb color, short localized label and symbol, while existing typed microphone/answer controls retain authority. Silent thinking never finishes an answer. Generation/grading completion must remain observable without another model tool request, and later learner speech must not hide a verified same-question completion or authorize automatic readback.
- Topic discovery, settings changes, creation/deletion, greetings and connection checks are not learning. After the call, remaining eligible original transcript evidence and immutable focus/revision metadata identify genuine exchanges for canonical voice-learning records. Before a canonical QUESTION answer is submitted, its exact question and USER source rows are excluded from post-call learning eligibility so they cannot create a duplicate `VOICE_TUTOR` record; private transcript history stays intact. Setup-only conversation creates no scored learning progress. Original microphone transcripts remain private evidence, while the submitted QUESTION answer is the learner-reviewed text. This review flow does not establish that every original ASR word was spoken. Recognition failure leaves the draft available for typing and correction; incomplete evidence cannot produce duplicate post-call learning records.
- Trusted question-change events refresh the exact canonical record in iOS and recheck changed records when the call ends. The active question selection and record-ID-keyed answer draft remain the learner's own; an incoming generated question, saved voice answer or grading result cannot replace a different selected question or overwrite a draft.
- Tool calls may briefly wait internally for the exact source learner/confirmation rows to finish saving. A tutor preamble such as “바꿀게요” does not supersede that learner request; only newer learner speech does. The learner must not be asked to repeat a command because transcription or persistence is still catching up. Native model observations never replace ownership, exact-ID or transaction checks.

#### Shared requirements and legacy compatibility details

The native interruption contract above supersedes the legacy no-interruption and assessed-input reply gates in requirement 11. Descriptions of independently assessed turns, spoken-offer attestation and live question verification below remain legacy-only; shared lifecycle and ownership requirements still apply. The PCM fallback is unchanged by the native interruption fix.

1. An authenticated member with an effective TIER2 or TIER3 entitlement can start a live, two-way voice call without selecting a topic first. The tutor's first utterance is a direct topic-discovery question in the accepted session language, without a greeting or self-introduction; it then finds the learner's saved topic and follows its actual child branches conversationally. An empty saved-study list does not block connecting and never creates a fallback study. TIER1 receives a localized Pro-upgrade explanation and no realtime credential or stream allocation.
2. The first release is foreground-only. iOS requests microphone permission immediately before the first lesson, uses the BuddyStudy voice-session API while the lesson screen is active, and ends the session when the app backgrounds, the device locks, the account changes, or the screen is dismissed. Audio background mode and unattended continuation are out of scope.
3. `GET /api/v1/voice-tutor/status` is the client authority for availability, remaining seconds, reset time, the operator-configured per-session ceiling, and optional-recording availability. `POST /api/v1/voice-tutor/sessions` derives and atomically reserves the next-session maximum as no more than the smaller of the remaining monthly allowance and that ceiling. New iOS clients POST an audio-only SDP offer to `/api/v1/voice-tutor/sessions/{id}/webrtc`, carry microphone/model media directly over the resulting OpenAI WebRTC peer connection, and use the authenticated `/control` WebSocket with `buddystudy.voice.control.v2` for server-owned turn control and lifecycle. Both requests require `X-Voice-Turn-Protocol: realtime-native-v1`; an older client is rejected before creating or claiming a provider call. `/stream` with `buddystudy.voice.v1` remains the bounded PCM fallback.
4. Voice allowance is counted in integer seconds. The server-owned plan default is 3,600 seconds per monthly window for both TIER2 and TIER3 and zero for TIER1. Operators can change each tier's `monthlyVoiceSecondsLimit` without an app release and can set a nullable per-user monthly override without resetting that user's period or counters. The exact administrative override value `31,536,000` seconds is presented by the app as effectively unlimited rather than as rounded minutes; it does not remove the per-call provider ceiling. `VOICE_TUTOR_MAX_SESSION_SECONDS` independently changes the operational cap for one call, defaults to 3,600 seconds, and is hard-clamped to the provider's 60-minute Realtime session limit. The default 60 monthly minutes may be used in one call or split across shorter calls. Apart from the effectively-unlimited convention, the app displays rounded minutes but never calculates entitlement or authoritative usage locally.
5. The server timestamps the accepted session, owns the WebRTC call and authenticated sideband lifecycle, reserves capacity transactionally, and settles server-observed rounded-up connected time exactly once. The reservation freezes whether that session will exhaust its finite monthly allowance at its hard end, so a normal per-call/provider deadline is never misreported as monthly exhaustion. The legacy PCM fallback additionally meters accepted decoded PCM and charges the greater value. It releases unused reservation after normal end or failure and expires abandoned sessions. Concurrent starts cannot reserve the same remaining seconds twice, and client-provided duration never determines charged usage.
6. Voice time and question allowance remain separate. Starting, ending, summarizing, or syncing a voice lesson itself consumes no question quota and creates no question. An explicit new-question request during the native lesson uses ordinary question generation and its quota; the learner's explicitly reviewed answer uses ordinary answer submission and grading. Manual voice answer editing uses the existing record-ID-keyed draft repository. An existing draft is loaded and preserved until the learner explicitly edits or submits it; incoming recognition alone must not overwrite its stored value. Skip, new-question delivery, grading, and synchronization never clear drafts or change the active question selection.
7. Ending a session explicitly through `POST /api/v1/voice-tutor/sessions/{id}/end`, or implicitly through a terminal stream close, always settles the call but produces a private Tutor Learning Result only after the server has authorized one substantive question for a confirmed saved focus, semantically verified the exact completed tutor-audio item as that one question, and durably linked the learner's exact complete answer to it. If no such actual question-and-answer exchange exists, the backend must not invoke the summary model, regardless of transcript length or whether setup actions succeeded. A long answer may span multiple persisted parts, but the parts qualify only as one ordered, duplicate-free, same-revision set with no intervening tutor turn; the result model and canonical projector must accept all of that set or none of it. Topic discovery, root/topic creation, settings changes, focus selection, consent and other setup-only dialogue never qualify as learning: they skip the summary model, complete with an empty technical result so clients stop polling, and create neither a canonical nor public record. Eligible sessions expose only the source-backed question, complete learner answer, and any exact validated final feedback to the bounded summary request; their validated node-linked exchanges become canonical `VOICE_TUTOR` records alongside `QUESTION` records, not a second collection of posts. Full transcripts, session/turn identities and recordings remain owner-only. Spoken assessments do not enter ordinary generated-question or topic-growth calculations without an explicit assessment policy.
8. Realtime microphone/model frames are never written to MySQL, application logs, analytics, Sentry, MCP, or backups. Optional recording is a separate default-off capability: only a session created with explicit `voice-recording-v1` consent may mix the learner and tutor tracks locally into one AAC/M4A file and upload it directly to private S3. The backend validates signed content type, exact length, and SHA-256 before making it available; the owner receives only short-lived playback URLs, may delete it immediately, and the default configurable retention is 30 days from the server-recorded call end. Reissuing the same pending upload grant cannot extend that absolute deadline, and playback grants fail closed at the boundary. Account withdrawal first commits an independent permanent recording-prefix cleanup tombstone, attempts private-object deletion, continues relational cleanup even if S3 is unavailable, retries deletion minutely through the signed-URL expiry safety deadline and daily forever afterward, and requires bucket lifecycle expiry as a storage-level backstop. Bounded transcript turns and the derived result may still be stored for private lesson history, while voice endpoint bodies, SDP, control frames, transcript text, summaries, object keys, presigned URLs, and provider credentials stay excluded from API/external-provider logs, analytics, and Sentry attachments.
9. The MCP server exposes authenticated, owner-scoped, read-only `list_voice_tutor_sessions`, `get_voice_tutor_session`, and `get_voice_tutor_quota` tools plus the `buddystudy://voice-tutor/sessions/recent` and `buddystudy://voice-tutor/quota` resources. Its general question tools include `list_pending_questions` with optional exact `study_id` filtering before counting/pagination, and `skip_question` for an explicitly requested skip of one unsubmitted UNGRADED question. Repeating an already completed skip preserves its original timestamp; submitted or grading answers cannot be skipped or revived by a late submission. MCP may return ordinary owner-scoped recording metadata through session detail, but never an audio object, object key, upload grant, or presigned playback URL; it never starts, streams, reconnects, ends, extends, records, downloads, or deletes a voice session.
10. Microphone denial, an interrupted audio route, network loss, quota exhaustion, and provider failure all produce explicit recoverable or terminal states. When the reserved session reaches actual monthly exhaustion during a live WebRTC call, the server closes learner input, asks the tutor to speak one short localized exhaustion notice, and identifies that exact response on the sanitized control stream. Settlement and transport teardown wait for that marked provider response to complete, its output audio buffer to stop, and the client to acknowledge that the same response's local playout has drained. When monthly exhaustion and the provider's 3,600-second hard limit are the same boundary, the server may pre-arm the notice up to eight seconds before hard end; that notice consumes the final reserved service seconds, the client keeps showing their countdown, and settlement occurs at the exact hard boundary. A notice generation that produces no audible evidence within three seconds is cancelled and retried exactly once, while a notice that has started speaking is allowed to finish without regeneration. An ordinary 60-minute per-call/provider `TIME_LIMIT` remains distinct, must not claim the monthly allowance is exhausted, and follows its own terminal path. A reserved session has one relay claim: a disconnect is finalized and a retry creates a new session from the remaining monthly allowance, rather than opening a second provider socket against the old reservation. A final result and quota settlement remain idempotent when end requests race or repeat.
11. In the legacy `local-vad-v1`/PCM conversation path only, a learner who starts speaking over the tutor does not stop or truncate the tutor's current audio. Every ordinary tutor response is one short, complete sentence; the app plays that sentence through while continuing to capture the learner, and the backend answers the coalesced committed learner turn only after the same response has reached provider completion, its OpenAI output buffer has stopped, and the learner has stopped. WebRTC provider turn detection is explicitly disabled and confirmed before ready because provider VAD can clear output despite disabled response interruption. The app automatically detects speech boundaries from its existing processed microphone path, independently of recording consent, and sends only numbered start/stop signals; no push-to-talk action is required and tutor speech never mutes the microphone. The backend owns input commits and waits for their provider acknowledgement. Client-originated input commits/clearing, response cancellation, audio truncation, session updates, and response creation are rejected on `/control`; the direct WebRTC offer is audio-only, so provider control remains on the backend sideband. Long learner speech is split into bounded internal transcription checkpoints without stopping capture; elapsed time, a meaningful checkpoint or an important misconception never permits the tutor to speak over an ongoing utterance. Only the final stopped, acknowledged, assessed and persisted turn can open the normal reply gate.
12. Once media and control are ready, the tutor speaks first with only a short, direct topic-discovery question such as “어떤 주제로 이야기해 볼까요?” It does not greet, introduce/name itself, describe itself as an AI/tutor/teacher, use a lead-in, choose a predetermined topic, or require a readiness check. Only when the learner directly asks about its identity may it answer that identity question. An ordinary first topic-bearing learner utterance authorizes discovery only, even when it names a precise saved descendant or asks to begin it. A create-and-start or update-and-start request instead follows requirement 15: one exact mutation question must include immediate learning, fresh agreement confirms it, and the server-owned write/readback/focus pipeline must succeed before teaching. For ordinary saved-tree discovery, the tutor uses small owner-scoped search pages and exact parent/child relationships, follows a complete single-child chain without making the learner repeatedly choose, and at the first real branch speaks at most three actual returned children. It must then speak the exact verified endpoint or branch candidates and wait for one new final meaningful learner reply before selecting an exact target or teaching it. A contextual yes after that spoken proposal is sufficient and is not followed by another readiness check. A greeting such as “안녕”, a microphone check, the original broad request, tool arguments and ordinary tool-result text are neither target confirmation nor a lesson-ending command. Connection failure is never presented as successful lesson completion; cleanup preserves a retryable failure state, clears the live countdown, and refreshes the server-owned quota. Reserved time is distinguished from used time and released capacity is reflected after settlement.
13. The speaking indicator reflects locally rendered tutor audio, not just server-side generation. An interrupted native response immediately leaves the speaking state, and late events for that response cannot restart it. Continuous digital-silence buffers must not keep a completed sentence waiting indefinitely; the separate terminal playout fences continue to account for device output latency. Diagnostics distinguish connection success, media rendering, and device playout without logging speech or credentials.
14. The live call uses one central tutor orb on a quiet, minimal surface with only the information needed for the current state. Tapping the orb requests the acknowledged `pause-v1` operation; the UI remains pending until the matching server ACK establishes pause, and a second tap restores listening only after the resume ACK and input-buffer fence. Dragging the orb upward continuously reveals the persistent full-screen conversation, and dragging it downward returns to the call. The orb and transcript stay mounted and follow the finger throughout the transition; learner-right/tutor-left history scrolls independently. Holding the orb enters a visible preparation stage at 0.35 seconds, shows an explicit keep-holding-to-end instruction at 0.9 seconds, and ends the call once only after 2.2 seconds of uninterrupted holding. After hold preparation begins, releasing, moving, or cancelling before the end threshold cancels termination and must not trigger a pause/resume tap. A short release before the hold stage remains the ordinary tap action. Gesture cancellation, screen exit, and a new call attempt invalidate any pending hold. The app tab bar is hidden in this destination. Failure recovery, recording consent, pause state, remaining time, and learning-result details remain available without competing with the orb. Performance traces, standalone session replay, advertising identifiers, and PostHog collection are not part of the app.

8. ### Community

Public-question options are owner-aware. The authenticated backend returns `isOwnedByMe` from the canonical record owner for feed, detail, search and liked pages, including when author profile display data is unavailable. My own question offers only Make private and Delete; it has no Edit, Report or Block action. Other users' questions retain moderation actions. Older responses without the field may use a resolved numeric account/author identity; unknown ownership must not be treated as another author while the profile is loading.

1. Community questions are available only after Google Login.
2. A signed-in user can maintain a public profile with display name and a short bio.
3. Public community questions include the author's display name and a simple in-app pixel avatar. User-uploaded profile photos are not supported.
4. Question-publicity defaults to private for non-signed-in users.
5. Signed-in users can report public questions and block abusive users. Reports are persisted by the backend and may be forwarded to the operator email when SMTP is configured. Blocking immediately hides the blocked user's public questions and comments for the blocker, rejects direct access to that user's public-question detail, and remains enforced by the backend across devices.
6. The legacy `/api/v1/public/questions` contract returns one ordered `items` list whose discriminated item type is either `PUBLIC_QUESTION` or `ADVERTISEMENT`; it remains supported for older apps and as the first-party fallback inventory. iOS renders that order without selecting, ranking, or repositioning campaigns. Every Coupang advertisement contains its provider name, optional product image, localized advertising label, title, optional body, full affiliate disclosure, server-generated `selectionId`, and HTTPS Coupang advertising URL. The iOS advertisement row follows the public-question card hierarchy and neutral primary/secondary text colors without inheriting the blue link tint, places `쿠팡`/`Coupang` in the topic position, and places the full affiliate disclosure immediately below that topic/advertising meta and before the promoted content in a compact neutral notice band. The disclosure remains visible without truncation, collapses operator-entered whitespace to natural word spacing, and wraps at the available card width. A trailing product thumbnail appears only after a valid HTTPS image loads; otherwise the content uses the full row width without an empty image placeholder. The server requires enough surrounding questions, keeps ads away from the first two rows and the end of the page, and ranks eligible campaigns from business priority, authenticated/anonymous relevance, Bayesian-smoothed 30-day destination-open rate, freshness, exploration, and Bayesian-smoothed not-interested rate. Ranking reads per-user and per-campaign signals in bounded batch queries rather than once per campaign. Daily selection caps, minimum selection intervals, and post-open cooldowns prevent fatigue; 85% of eligible selections exploit the top result and 15% explore the remaining top three. The durable selection history is the ranking source of truth. When at least 50% of an ad row remains on screen for one second, iOS idempotently records `impression_at`; this is distinct from server delivery. Opening the destination publishes one idempotent `NATIVE_AD_VIEWED` event through the transactional Outbox and `community.native-ad.view.v1`; iOS does not maintain ad-ranking history. `관심 없음` immediately removes the card and persists a user-scoped permanent campaign exclusion before future ranking, including on the user's other devices; failures restore the optimistically removed card, while successful suppressions also lower campaign-wide ranking quality. Monitoring `Advertising` is list-first and lets an authenticated operator search campaigns by key or localized title, filter by active/paused/scheduled/ended status and audience, create, schedule, pause, and edit campaigns, enter localized copy, an optional Coupang CDN image, full disclosures, and a validated Coupang URL, tune the ranking/fatigue/position controls, and inspect the exact live ranking formula. The campaign list reports 30-day feed deliveries, verified viewport impressions, destination opens, viewable open rate, not-interested count, and not-interested rate. A paginated per-campaign audience view supports user search and opened/not-opened filters, aggregates delivery/impression/open counts and timestamps per user, redacts anonymous or withdrawn identities, and never exposes raw device identifiers.
7. The current iOS client uses `GET /api/v2/public/questions`. Only the unfiltered first page may contain at most one server-positioned `NATIVE_AD_SLOT`; search, liked questions, and later offset pages never contain a slot. Anonymous users and active TIER1 users are eligible, while TIER2 and TIER3—including a scheduled downgrade before the paid entitlement expires—receive an ad-free public feed. If entitlement resolution is uncertain, the server omits the slot. The `COMMUNITY_FEED` policy is OFF by default and controls its active period, per-user UTC daily cap, minimum interval, minimum question count, and placement range; transactional reservation prevents concurrent requests from exceeding the cap. Regardless of operator values, the server keeps the slot after at least two questions and before the final question and validates a minimum 60-second interval. iOS requests a non-personalized, teen-rated AdMob native ad only after the current-launch UMP refresh and consent gathering succeed and `canRequestAds` is true. When `IABTCF_gdprApplies` says European regulations apply, the IAB TCF Purpose 1 consent string must also permit storing or accessing device information; US-state decisions instead use the GPP signal written by UMP. No ATT prompt, IDFA, BuddyStudy user/device identifier, search term, topic, content URL, or keyword is supplied. BuddyStudy does not request Limited Ads after European Purpose 1 denial/unknown state or a UMP update/form failure. AdMob success owns the slot; those privacy-gate failures, SDK error, no-fill, or the five-second timeout trigger one lazy first-party fallback request, and a late or pre-choice AdMob callback cannot replace it. There is no automatic refresh or immediate retry. AdMob delegate impressions and clicks are sent idempotently with provider `ADMOB`; first-party selections continue using their existing impression, open, not-interested, explanation, and inappropriate/age-inappropriate report paths. The deployable `Advertising` admin owns the common policy and reports 30-day slot delivery, AdMob impression/click, and fallback selection/impression/open totals.
8. Feedback opens a dedicated compact form and is stored independently from question reports.
9. Record, pending-question, public-question, and comment requests use `tl=ko|en|ja` with `view=localized|original`. Question, answer, AI response, and comment source languages are tracked independently. Manual and scheduled question creation, answer submission, grading completion, and comment creation enqueue missing supported-locale translations through the transactional Outbox; localized reads also repair missing or stale work while returning the original immediately. The legacy `language` query remains a temporary compatibility alias.
10. Canonical question and comment rows contain original text only. Translations are stored exclusively in per-content localization tables, and localized search uses the `(content ID, display language)` search read model rather than language-specific columns on the canonical row.
11. Answers use the selected display-language translation for every viewer, including the authenticated author; `view=original` is the explicit way to see the submitted text. Authenticated comment authors continue to see their own comments in the original language.

## Non-Goals

- Guaranteeing real-time push delivery independent of APNs behavior.
- Storing OpenAI billing balance locally as an authoritative source.
- Supporting app and content languages other than Korean, English, and Japanese in the current version.
- Calling OpenAI directly from the iOS or macOS app.
- Continuing a Voice Tutor session while the app is backgrounded or the device is locked in the first release.
- Persisting unconsented Voice Tutor microphone/model audio, exposing recording binaries through MCP, keeping recordings beyond the configured retention window, or enabling the default-off recording feature before the recording-specific privacy/legal release is approved.
